## 问题1：JavaScript 中 var、let、const 的核心区别是什么？分别在什么场景下使用？

### 核心区别

二者与var的核心差异集中在作用域、变量提升、重复声明、可变性四个维度，具体对比如下：

1. **作用域规则不同**

    - `var` 属于**函数作用域**，仅在声明它的函数内部有效，不受块级作用域（`if/for/{}代码块`）约束，极易造成变量污染。

    - `let/const` 属于**块级作用域**，仅在声明它的代码块内有效，出了块级作用域就无法访问，彻底解决了var的变量污染问题。

    ```JavaScript
    
    // var 示例：变量穿透块级作用域
    if (true) {
      var a = 10;
    }
    console.log(a); // 输出10，变量泄露到全局
    
    // let 示例：块级作用域隔离
    if (true) {
      let b = 20;
    }
    console.log(b); // 报错：b is not defined
    ```

2. **变量提升与暂时性死区**

    - `var` 存在**变量提升**，声明会被提升到当前作用域顶部，允许在声明前访问，值为`undefined`。

    - `let/const` 不存在变量提升，存在**暂时性死区（TDZ）**，在声明之前访问变量会直接抛出引用错误，强制开发者养成“先声明后使用”的规范。

    ```JavaScript
    
    console.log(num1); // 输出undefined，变量提升生效
    var num1 = 100;
    
    console.log(num2); // 报错：Cannot access 'num2' before initialization
    let num2 = 200;
    ```

3. **重复声明限制**

    - `var` 允许在同一作用域内重复声明同一个变量，后声明的会覆盖先声明的，极易造成逻辑bug。

    - `let/const` 禁止在同一作用域内重复声明同一个变量，声明时会直接抛出语法错误，提前规避问题。

4. **赋值与可变性限制**

    - `var/let` 允许声明后重新赋值，无任何限制。

    - `const` 声明时**必须同时赋值**，且声明后不允许重新赋值；针对引用类型（对象/数组），仅限制内存地址不可修改，对象的属性、数组的元素仍可正常修改。

    ```JavaScript
    
    const PI = 3.1415;
    PI = 3.14; // 报错：Assignment to constant variable
    
    const user = { name: "张三" };
    user.name = "李四"; // 合法，仅修改属性，未修改内存地址
    user = { name: "王五" }; // 报错，重新赋值修改了内存地址
    ```

### 适用场景

- **var**：ES6+开发环境下**不推荐使用**，仅用于兼容极低版本浏览器的特殊场景。

- **let**：用于需要频繁重新赋值的变量，比如循环计数器、状态切换的标志位、接口返回的动态数据等。

- **const**：优先推荐使用，用于所有不需要重新赋值的场景，包括常量、固定配置项、引用类型的对象/数组、函数表达式等，可有效避免意外赋值导致的bug。

## 问题2：浏览器从输入URL到页面完整渲染，核心流程分为哪几个阶段？每个阶段的关键动作是什么？

整个流程可分为**网络请求、解析构建、渲染绘制**三大核心阶段，每个阶段环环相扣，具体细节如下：

### 第一阶段：网络请求阶段（获取页面资源）

核心目标：通过网络请求，从服务器获取到页面的HTML核心资源及依赖资源。

1. **URL解析与安全校验**：浏览器先解析输入的URL，区分协议、域名、端口、路径、参数等信息，同时校验URL是否符合安全规范，是否存在跨域、恶意地址等风险。

2. **DNS域名解析**：将域名转换为服务器的IP地址，优先读取浏览器DNS缓存→系统DNS缓存→本地hosts文件→向本地DNS服务器发起递归查询→根DNS服务器迭代查询，最终获取目标服务器IP。

3. **TCP连接建立**：基于IP地址与服务器建立TCP连接，通过**三次握手**确认双方收发能力正常；若为HTTPS协议，会在此步骤额外完成TLS/SSL握手，建立加密传输通道。

4. **HTTP请求发起与响应**：浏览器向服务器发起HTTP/HTTPS请求，携带请求头、Cookie、参数等信息；服务器接收请求后，处理业务逻辑，返回对应的响应头、状态码、HTML文档主体。

5. **TCP连接关闭**：资源传输完成后，通过**四次挥手**正常断开TCP连接；若开启了HTTP长连接（Connection: keep-alive），连接会持续保留，用于后续同域名资源的请求复用。

### 第二阶段：解析与构建阶段（生成渲染所需的核心树结构）

核心目标：将获取到的资源解析为浏览器可识别的结构，为渲染做准备。

1. **HTML解析生成DOM树**：浏览器自上而下解析HTML文档，将标签转换为DOM节点，去除空格、注释等无效内容，最终生成一棵完整的**DOM树（文档对象模型）**；解析过程中若遇到script标签，会默认暂停HTML解析，优先下载并执行JS代码（JS可修改DOM结构，避免渲染冲突）。

2. **CSS解析生成CSSOM树**：解析style标签、link引入的CSS样式表，处理样式继承、层叠优先级，将每个CSS规则转换为对应的节点样式，最终生成**CSSOM树（CSS对象模型）**。

3. **合成渲染树（Render Tree）**：将DOM树与CSSOM树进行合并，只保留可见的节点（排除display: none的节点、head标签等不可见内容），为每个节点匹配对应的样式，最终生成**渲染树**，只包含渲染页面所需的节点与样式信息。

### 第三阶段：渲染与绘制阶段（将内容呈现到屏幕上）

核心目标：基于渲染树，完成页面的布局、绘制与展示。

1. **布局（Layout/回流）**：根据渲染树，计算每个节点在页面中的精确位置和大小，比如盒子模型的宽高、边距、在视口中的坐标，确定所有元素的几何信息，这个过程也叫**回流**。

2. **绘制（Paint/重绘）**：基于布局阶段的几何信息，为每个节点填充像素内容，包括颜色、背景、边框、阴影、文字等，将元素的视觉样式绘制到对应的图层上，这个过程也叫**重绘**。

3. **合成（Composite）**：将绘制好的多个图层，按照正确的层级顺序合并，最终提交到GPU，渲染到屏幕上，用户即可看到完整的页面内容。

### 关键补充

- 回流必然触发重绘，重绘不一定触发回流（比如只修改颜色，不改变元素位置大小，只会触发重绘）；

- 优化页面渲染性能的核心，就是尽可能减少回流与重绘的次数。

## 问题3：前端页面性能优化有哪些核心方向？有哪些可落地的实操方案？

前端性能优化的核心目标是**缩短页面首屏加载时间、提升页面交互流畅度、降低资源消耗**，核心分为5大方向，每个方向均有可直接落地的实操方案：

### 一、网络传输层优化：减少资源加载耗时

核心逻辑：减少请求体积、缩短请求链路、提升传输效率。

1. **资源压缩与合并**

    - 开启Gzip/Brotli压缩，可将文本类资源（HTML/CSS/JS）体积压缩60%以上，服务端配置即可生效；

    - 压缩图片资源：优先使用WebP/AVIF等新一代图片格式，配合图片懒加载，大图片使用渐进式加载；通过工具压缩图片，避免原图直接上线；

    - 精简代码：通过构建工具开启Tree-Shaking，剔除未使用的死代码；压缩混淆JS/CSS代码，去除注释、空格、变量名简化。

2. **请求链路优化**

    - 静态资源全量接入CDN，利用CDN边缘节点缩短资源请求的物理距离，降低延迟；

    - 升级HTTP/2或HTTP/3，支持多路复用、头部压缩、服务器推送，彻底解决HTTP1.1的队头阻塞问题；

    - 开启DNS预解析`rel="dns-prefetch"`、预连接`rel="preconnect"`，提前对跨域域名进行DNS解析和TCP握手，减少后续资源请求的耗时。

3. **请求数量优化**

    - 小图片、小图标转为雪碧图、Base64或SVG图标，减少HTTP请求次数；

    - 合理设置资源合并策略，避免单个资源体积过大，也避免过多碎片化的小资源请求。

### 二、渲染层优化：减少页面渲染耗时

核心逻辑：缩短关键渲染路径，减少回流与重绘，提升渲染效率。

1. **关键渲染路径优化**

    - 关键CSS内联到HTML头部，避免CSSOM阻塞渲染；非关键CSS异步加载，减少首屏渲染阻塞；

    - 优化script标签：非关键JS添加`defer/async`属性，defer会在HTML解析完成后按顺序执行，async会在下载完成后立即执行，避免JS阻塞HTML解析；

    - 减少DOM节点数量，DOM节点越多，解析和布局耗时越长，首屏优先渲染核心内容，非核心内容延迟渲染。

2. **回流与重绘优化**

    - 避免频繁修改DOM样式，集中修改样式（比如通过修改class一次性修改多个样式，而非逐条修改style属性）；

    - 对频繁触发回流的元素（比如动画元素），开启GPU加速，提升到独立合成图层，避免影响其他元素的渲染；

    - 离线操作DOM：通过DocumentFragment批量操作DOM，操作完成后再一次性插入到页面中，减少回流次数。

3. **首屏体验优化**

    - 增加骨架屏、Loading占位，减少用户等待的感知时长；

    - 实现服务端渲染（SSR）/静态站点生成（SSG），直接返回带内容的HTML，缩短首屏白屏时间，同时利于SEO。

### 三、代码与交互层优化：提升运行时性能

核心逻辑：优化代码执行效率，避免卡顿，提升交互流畅度。

1. **JS执行优化**

    - 高频触发的事件（scroll、resize、input、mousemove）添加**防抖（debounce）/节流（throttle）**，限制事件回调的执行频率，避免JS频繁执行阻塞主线程；

    ```JavaScript
    
    // 节流：固定时间内只执行一次，适用于滚动、resize场景
    function throttle(fn, delay = 200) {
      let lastTime = 0;
      return function (...args) {
        const now = Date.now();
        if (now - lastTime >= delay) {
          fn.apply(this, args);
          lastTime = now;
        }
      };
    }
    
    // 防抖：触发后延迟执行，期间再次触发则重置计时，适用于搜索输入、按钮点击场景
    function debounce(fn, delay = 300) {
      let timer = null;
      return function (...args) {
        clearTimeout(timer);
        timer = setTimeout(() => fn.apply(this, args), delay);
      };
    }
    ```

    - 避免长任务阻塞主线程：JS是单线程执行，超过50ms的任务即为长任务，会阻塞页面渲染和交互响应；可通过Web Worker将耗时的计算任务放到独立线程执行，不占用主线程。

2. **资源懒加载与按需加载**

    - 图片、视频等媒体资源实现懒加载，只加载视口内的资源，滚动到对应位置再加载后续资源；

    - 路由级别的代码分割，单页应用（SPA）通过动态import实现路由按需加载，避免首屏一次性加载全量JS代码；

    - 组件级别的懒加载，非首屏的复杂组件（弹窗、侧边栏、底部内容）实现延迟加载，减少首屏打包体积。

### 四、缓存策略优化：减少重复资源请求

核心逻辑：利用浏览器缓存，避免重复请求相同的资源，实现“一次加载，多次复用”。

1. **强缓存**：通过设置`Cache-Control: max-age=xxx`、`Expires`响应头，设置资源的强缓存时间，在缓存有效期内，浏览器直接从本地读取资源，不会向服务器发起任何请求，性能最优；适合长期不变的静态资源（图片、字体、打包后的JS/CSS）。

2. **协商缓存**：通过设置`Last-Modified/If-Modified-Since`、`ETag/If-None-Match`响应头，浏览器发起请求时，服务器校验资源是否发生变化，未变化则返回304状态码，浏览器直接读取本地缓存；适合频繁更新的资源（HTML、接口数据）。

3. **进阶缓存方案**

    - 利用Service Worker实现离线缓存，自定义缓存规则，实现离线访问、资源预缓存等能力；

    - 合理使用本地存储（localStorage/sessionStorage），缓存不敏感的非高频更新数据，比如用户配置、静态文案、接口的非实时数据。

### 五、兜底体验优化：避免异常场景的体验降级

- 针对弱网环境，实现资源降级方案，比如低清晰度图片、精简版页面；

- 接口异常时，添加友好的错误提示和重试机制，避免页面白屏；

- 针对低版本浏览器，添加polyfill兼容，避免页面功能异常。

## 问题4：Vue3 的 Composition API（组合式API）与 Options API（选项式API）核心区别是什么？各自的适用场景是什么？

### 核心定义

- **Options API（选项式API）**：Vue2的默认API风格，通过固定的`data、methods、computed、watch、生命周期钩子`等选项组织代码，是Vue经典的开发模式。

- **Composition API（组合式API）**：Vue3新增的核心API，通过`setup`语法糖、响应式API（ref/reactive）、组合式函数，基于业务逻辑组织代码，是Vue3推荐的开发模式。

### 核心区别

|对比维度|Options API|Composition API|
|---|---|---|
|**代码组织方式**|基于选项拆分代码，同一个业务逻辑的代码会分散到data、methods、computed、watch等多个选项中|基于业务逻辑拆分代码，同一个功能的响应式数据、方法、计算属性、监听可以集中写在一起，逻辑内聚性更强|
|**逻辑复用能力**|主要通过mixins实现逻辑复用，存在命名冲突、来源不清晰、隐式依赖等问题，复用性差|基于组合式函数（Composables）实现逻辑复用，纯函数式写法，无命名冲突，依赖清晰，可无限组合，复用性极强|
|**TypeScript支持**|对TS支持不友好，类型推导复杂，需要额外的装饰器辅助，开发体验差|原生完美支持TS，类型推导丝滑，无需额外配置，是TS项目的首选方案|
|**响应式实现**|基于Object.defineProperty实现响应式，存在数组、对象深层属性监听的缺陷|基于Proxy实现响应式，完美支持数组、对象深层属性、Map/Set等数据结构，无监听缺陷|
|**打包体积**|基于选项的固定结构，无法被Tree-Shaking优化，未使用的选项也会被打包进产物|函数式写法，可被Tree-Shaking深度优化，未使用的API不会被打包，产物体积更小|
|**上手门槛**|规则固定，选项职责清晰，新手极易上手，符合直觉|灵活性更高，需要理解响应式原理和JS函数式编程，上手门槛略高|
### 代码示例对比

```Plain Text

<!-- Options API 写法 -->
<template>
  <div>
    <p>计数：{{ count }}</p>
    <p>双倍计数：{{ doubleCount }}</p>
    <button @click="addCount">增加</button>
  </div>
</template>
<script>
export default {
  // 数据单独写在data选项
  data() {
    return {
      count: 0
    };
  },
  // 计算属性单独写在computed选项
  computed: {
    doubleCount() {
      return this.count * 2;
    }
  },
  // 方法单独写在methods选项
  methods: {
    addCount() {
      this.count++;
    }
  },
  // 生命周期单独写在对应选项
  mounted() {
    console.log("组件挂载完成", this.count);
  }
};
</script>
```

```Plain Text

<!-- Composition API 写法（setup语法糖） -->
<template>
  <div>
    <p>计数：{{ count }}</p>
    <p>双倍计数：{{ doubleCount }}</p>
    <button @click="addCount">增加</button>
  </div>
</template>
<script setup>
import { ref, computed, onMounted } from "vue";

// 同一个业务逻辑的代码集中在一起
// 1. 响应式数据
const count = ref(0);
// 2. 计算属性
const doubleCount = computed(() => count.value * 2);
// 3. 操作方法
const addCount = () => {
  count.value++;
};
// 4. 生命周期钩子
onMounted(() => {
  console.log("组件挂载完成", count.value);
});
</script>
```

### 各自的适用场景

#### Options API 适用场景

1. 小型项目、简单页面、低复杂度组件，业务逻辑单一，无需复杂的逻辑复用；

2. 新手入门Vue，学习成本低，固定的选项结构能快速上手，理解Vue的核心概念；

3. 维护Vue2的老项目，无需重构的场景，保持代码风格统一。

#### Composition API 适用场景

1. 中大型项目、高复杂度组件，业务逻辑多，需要将不同功能的逻辑拆分、集中管理，提升代码可维护性；

2. 需要大量逻辑复用的场景，通过组合式函数封装通用逻辑（比如分页、表单校验、权限控制、请求封装），替代mixins，解决复用痛点；

3. TypeScript开发的项目，完美的类型支持能大幅提升开发效率，减少类型bug；

4. 对打包体积有严格要求的项目，更好的Tree-Shaking支持能有效减小产物体积。

### 补充说明

Vue3完全兼容Options API，二者可以在同一个项目中混用，无需强制切换；但对于Vue3的新项目，官方优先推荐使用Composition API，尤其是`<script setup>`语法糖，是Vue3的主流开发模式。

## 问题5：前端工程化体系包含哪些核心模块？日常开发中如何落地？

### 核心定义

前端工程化，是指用系统化、标准化、自动化的方案，解决前端开发过程中的**效率、质量、协作、维护、部署**等一系列问题，覆盖前端项目从初始化到上线的全生命周期，是现代前端开发的核心基础。

### 核心模块与落地方案

前端工程化体系分为6大核心模块，每个模块都有成熟的落地方案，可直接在日常开发中落地：

#### 一、模块化与组件化：工程化的基础核心

模块化与组件化是前端工程化的基石，核心目标是解决代码的复用、拆分、维护问题，避免代码耦合与冗余。

1. **模块化落地**

    - **JS模块化**：统一使用ES Module（ESM）规范，通过`import/export`实现代码的导入导出，替代老旧的CommonJS规范，适配浏览器与构建工具的原生支持；

    - **CSS模块化**：使用CSS Modules、Scoped CSS、Less/Sass等预处理器，解决CSS全局污染问题，实现样式的模块化隔离；

    - **资源模块化**：通过构建工具，将图片、字体、音频等静态资源当作模块处理，实现按需引入、哈希命名、自动压缩等能力。

2. **组件化落地**

    - 基于Vue/React等框架，实现**基础组件-业务组件-页面组件**的三级组件体系；

    - 基础组件：通用的UI组件（按钮、输入框、弹窗等），无业务逻辑，可跨项目复用，可基于Element Plus/Ant Design Vue二次封装；

    - 业务组件：封装当前项目的通用业务逻辑，比如商品卡片、地址选择器、搜索组件等，在项目内复用；

    - 页面组件：对应具体的路由页面，由基础组件和业务组件组合而成。

#### 二、构建与编译工具：工程化的核心载体

构建工具是前端工程化的核心，负责代码的编译、打包、压缩、转换，解决浏览器兼容性、资源优化、开发效率等问题。

1. **开发环境搭建**

    - 新项目优先使用**Vite**作为构建工具，基于原生ESM，开发环境启动速度极快，热更新无延迟，适配Vue/React/原生JS等多种技术栈；

    - 老项目可使用**Webpack**，生态完善，适配复杂的构建场景，支持自定义loader和plugin，满足个性化构建需求；

    - 配置开发服务器，开启热更新（HMR）、代理转发（解决开发环境跨域问题）、source map（方便调试）。

2. **生产环境构建**

    - 配置代码压缩、混淆、Tree-Shaking，剔除死代码，减小打包体积；

    - 配置代码分割，拆分第三方依赖包、公共代码、路由代码，实现按需加载；

    - 配置资源哈希命名，解决浏览器缓存更新问题，避免静态资源缓存导致的线上更新异常；

    - 配置兼容性处理，通过Babel/SWC将ES6+代码转换为低版本浏览器可识别的语法，通过postcss-autoprefixer自动添加CSS浏览器前缀，解决兼容性问题。

#### 三、代码规范与约束：工程化的质量底线

核心目标是统一团队的代码风格，减少语法bug，提升代码的可维护性，避免“千人千码”的问题。

1. **编码规范落地**

    - **JS/TS规范**：使用**ESLint**配置代码校验规则，强制约束语法规范，比如禁止未使用的变量、禁止全局变量污染、强制使用===等；

    - **格式规范**：使用**Prettier**统一代码格式化规则，比如缩进、换行、引号、逗号等，彻底解决团队代码格式不一致的问题；

    - **配置统一**：在项目根目录统一存放`.eslintrc.js`、`.prettierrc`、`.editorconfig`配置文件，团队所有成员共用同一套规则，避免本地配置冲突。

2. **提交规范落地**

    - 使用**Commitlint**配置Git提交信息规范，强制使用`feat: 新增功能`、`fix: 修复bug`、`docs: 文档更新`等标准化提交格式，方便后续生成更新日志、代码回溯；

    - 使用**Husky + lint-staged**配置Git Hooks，在代码提交前，自动校验暂存区的代码规范，规范不通过则禁止提交，从源头杜绝不规范代码进入仓库。

#### 四、质量保障体系：工程化的风险防控

核心目标是通过自动化的手段，提前发现代码中的bug，保障线上代码的稳定性。

1. **单元测试**

    - 针对工具函数、通用组件、核心业务逻辑，编写单元测试用例，使用**Vitest**（适配Vite）/Jest作为测试框架，实现自动化测试；

    - 配置测试覆盖率阈值，要求核心代码的测试覆盖率不低于80%，避免核心逻辑出现bug。

2. **集成测试与端到端测试**

    - 针对核心业务流程，使用**Cypress/Playwright**编写E2E端到端测试用例，模拟用户的真实操作，验证页面功能是否正常，避免上线后出现流程阻断的问题。

3. **代码评审（Code Review）**

    - 建立团队CR规范，代码合并到主分支前，必须经过至少1人的评审，重点检查代码逻辑、性能、安全、规范问题，避免个人失误导致的线上bug。

#### 五、自动化部署与CI/CD：工程化的提效核心

核心目标是实现项目从代码提交到线上部署的全流程自动化，替代人工打包、上传、部署的繁琐操作，减少人为失误，提升发布效率。

1. **CI/CD流水线搭建**

    - 基于**GitHub Actions/GitLab CI/Jenkins**搭建自动化流水线，实现全流程自动化：

        1. 代码提交/合并到指定分支，自动触发流水线；

        2. 自动执行代码规范校验、单元测试，不通过则终止流水线，通知开发人员；

        3. 自动执行构建命令，生成生产环境的打包产物；

        4. 自动将产物部署到对应的测试/预发布/生产环境；

        5. 部署完成后，自动发送通知，告知团队部署结果。

2. **环境管理**

    - 区分开发环境、测试环境、预发布环境、生产环境，通过`.env`环境变量文件，配置不同环境的接口地址、域名、配置项，避免手动修改代码切换环境；

    - 实现灰度发布、版本回滚能力，线上出现问题时，可快速回滚到上一个稳定版本，降低故障影响范围。

#### 六、监控与运维体系：工程化的闭环保障

核心目标是线上项目的可观测、可追溯，及时发现线上问题，快速定位修复，形成工程化的完整闭环。

1. **前端监控落地**

    - 接入前端监控平台（比如Sentry、Fundebug），实时监控线上的JS报错、接口异常、白屏问题，捕获报错堆栈、用户信息、操作路径，快速定位问题；

    - 配置性能监控，采集页面首屏加载时间、LCP、FID、CLS等核心性能指标，持续优化页面性能；

    - 配置用户行为监控，采集用户的访问量、停留时长、操作路径，为产品优化提供数据支撑。

2. **线上运维**

    - 配置静态资源的回源策略、缓存策略，避免CDN缓存异常导致的线上问题；

    - 建立线上故障应急响应流程，明确故障上报、定位、修复、复盘的全流程规范。

## 问题6：前端常见的安全漏洞有哪些？如何针对性防范？

前端安全是项目上线的核心底线，前端作为用户与服务端的交互入口，是安全攻击的重灾区，以下是前端最常见的6大安全漏洞，以及对应的原理与可落地的防范方案：

### 一、XSS 跨站脚本攻击（最常见、危害最大）

#### 漏洞原理

攻击者在页面中注入恶意的JavaScript脚本，当用户访问页面时，恶意脚本会在用户的浏览器中执行，从而窃取用户的Cookie、Session、敏感信息，甚至冒充用户执行操作、篡改页面内容。

XSS分为3种类型：

1. **存储型XSS**：恶意脚本被存储到服务器数据库中，所有访问该内容的用户都会触发攻击，危害最大，常见于评论区、留言板、个人信息编辑等场景；

2. **反射型XSS**：恶意脚本拼接在URL中，诱导用户点击链接后，服务器将URL中的恶意内容反射到页面中执行，常见于搜索框、URL参数回显场景；

3. **DOM型XSS**：恶意脚本通过修改页面的DOM结构执行，全程在前端完成，不经过服务器，常见于前端通过URL参数、用户输入修改DOM内容的场景。

#### 针对性防范方案

1. **输入输出全量转义**：对用户输入的所有内容进行严格的转义，将`<、>、"、'、&`等特殊字符转换为实体字符，禁止用户输入的内容直接作为HTML代码执行；

2. **开启CSP内容安全策略**：在HTTP响应头中配置`Content-Security-Policy`，限制页面只能加载指定域名的资源，禁止执行内联脚本、eval函数，从根源上阻断恶意脚本的执行，是防范XSS最有效的手段；

    ```Plain Text
    
    # 示例CSP配置：只加载当前域名的资源，禁止内联脚本和eval
    Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:;
    ```

3. **禁止使用危险的API**：尽量避免使用`innerHTML、document.write、eval、setTimeout("字符串代码")`等可直接执行HTML/JS代码的API，如需渲染用户输入的内容，优先使用`innerText`；

4. **Cookie安全配置**：给核心Cookie添加`HttpOnly`属性，禁止JS读取Cookie，即使发生XSS攻击，也无法窃取用户的登录Cookie；同时添加`Secure`属性，只允许HTTPS协议传输Cookie。

### 二、CSRF 跨站请求伪造

#### 漏洞原理

攻击者诱导用户访问恶意网站，利用用户在目标网站已经登录的状态（浏览器会自动携带目标网站的Cookie），在用户不知情的情况下，冒充用户向目标网站发起恶意请求，执行非用户本意的操作（比如转账、修改密码、删除数据等）。

#### 针对性防范方案

1. **CSRF Token 校验**：这是防范CSRF最主流的方案。用户登录后，服务端生成一个唯一的CSRF Token，存储在用户Session中，前端每次发起请求时，都在请求头或请求参数中携带该Token，服务端校验Token是否有效，无效则拒绝请求；

2. **同源检测**：服务端校验请求的`Origin`和`Referer`请求头，确认请求的来源域名是否为合法域名，拒绝来自非法域名的请求；

3. **Cookie SameSite 属性**：给Cookie设置`SameSite=Strict/Lax`属性，禁止跨域请求携带Cookie，从根源上阻断CSRF攻击的核心条件，是目前浏览器原生支持的最优方案；

4. **关键操作增加二次校验**：比如修改密码、转账、删除数据等高危操作，增加验证码、密码二次确认、短信验证等步骤，即使发生CSRF攻击，也无法完成恶意操作。

### 三、点击劫持（UI覆盖攻击）

#### 漏洞原理

攻击者将目标网站通过iframe透明嵌套在恶意页面中，在页面上放置诱导用户点击的按钮（比如“领取红包”、“下载资源”），用户点击按钮时，实际点击的是透明iframe中的目标网站的按钮，在用户不知情的情况下，执行恶意操作（比如关注账号、开启权限、转账等）。

#### 针对性防范方案

1. **X-Frame-Options 响应头**：在服务端配置该响应头，禁止页面被iframe嵌套，是防范点击劫持最直接的方案，可选值：

    - `DENY`：完全禁止任何页面通过iframe嵌套；

    - `SAMEORIGIN`：只允许同域名的页面通过iframe嵌套；

2. **JS 防御**：在页面中添加JS代码，判断当前页面是否被嵌套在iframe中，若是则强制跳出iframe，让顶层页面显示当前页面；

    ```JavaScript
    
    if (top !== window) {
      top.location.href = window.location.href;
    }
    ```

3. **关键操作增加二次校验**：高危操作增加验证码、密码确认等步骤，避免被诱导点击完成恶意操作。

### 四、敏感信息泄露

#### 漏洞原理

前端代码中明文存储敏感信息、控制台输出敏感日志、HTTP明文传输数据、前端硬编码密钥等，导致用户的敏感信息（手机号、身份证号、密码、Token）、项目的配置信息、接口密钥泄露，被攻击者利用。

#### 针对性防范方案

1. **全链路HTTPS加密**：全站开启HTTPS协议，对传输的数据进行加密，避免HTTP明文传输被抓包窃取数据；

2. **敏感信息加密处理**：禁止前端存储明文密码，用户密码必须经过MD5/SM3哈希加盐后再传输到服务端；用户的身份证号、手机号等敏感信息，前端展示时必须脱敏处理（比如138****1234）；

3. **禁止前端硬编码敏感信息**：禁止在前端代码中硬编码服务端密钥、AK/SK、数据库账号等敏感信息，这类信息必须全部放在服务端；

4. **清理控制台敏感输出**：生产环境禁止通过console.log输出用户Token、接口参数、敏感信息，同时关闭生产环境的Vue/React DevTools，避免用户通过调试工具获取敏感信息；

5. **严格控制前端权限**：前端只存储当前用户的权限范围内的数据，禁止越权获取其他用户的信息，接口必须做权限校验，不能完全依赖前端的权限控制。

### 五、文件上传漏洞

#### 漏洞原理

攻击者利用页面的文件上传功能，上传恶意的脚本文件（比如.php、.js、.exe文件），如果服务端没有做严格的校验，文件被上传到服务器后，攻击者可通过URL访问执行该恶意文件，控制服务器，甚至获取整个网站的权限。

#### 前端针对性防范方案

1. **严格校验文件类型**：上传前校验文件的后缀名、MIME类型，只允许上传业务需要的文件类型（比如图片只允许.jpg/.png/.webp格式），禁止上传可执行的脚本文件；

2. **校验文件内容**：不能只通过后缀名判断文件类型，攻击者可修改后缀名绕过校验；针对图片文件，可通过Canvas读取图片的宽高，确认是合法的图片文件，避免恶意文件伪装成图片上传；

3. **限制文件大小**：上传前校验文件大小，禁止上传超大文件，避免服务器磁盘被占满；

4. **补充说明**：前端的校验只能拦截普通用户，攻击者可通过抓包修改请求绕过前端校验，**文件上传漏洞的核心防范必须在服务端完成**，前端仅作为第一道防线。
